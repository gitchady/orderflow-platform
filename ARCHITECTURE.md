# Architecture Overview

OrderFlow is an educational shop with six independent FastAPI applications and
a React storefront. Service source is under `<service>/app/`; each service has
its own dependency set and Docker image. There is no shared backend package.
Use `AGENTS.md` for operating commands and maintenance constraints, and
`README.md` for complete local setup.

# Microservices

| Location | Responsibilities and dependencies | Persistence | Messages |
| --- | --- | --- | --- |
| `api-gateway/` | `/api/auth`, `/api/products`, `/api/orders`; async HTTPX forwarding, JWT validation and order ownership | None | None |
| `auth-service/` | `/register`, `/login`; Argon2 hashing with pwdlib, HS256 JWT by default | PostgreSQL `auth-db`, `users` | None |
| `catalog-service/` | List/get/create products | PostgreSQL `catalog-db`, `products` | None |
| `order-service/` | Order reads/creation; synchronous HTTPX catalog/payment clients | PostgreSQL `order-db`, `orders`, `order_items` | Consumes RabbitMQ payment successes |
| `payment-service/` | Payment reads/creation and a four-second simulated success path | PostgreSQL `payment-db`, `payments`, async SQLAlchemy | Produces same success event to RabbitMQ then Kafka |
| `analytic-service/` | Background Kafka consumer and `/events?limit=20` | Async PyMongo, MongoDB `analytics.events` by default | Consumes Kafka payment events |

# Service Communication

Browser requests default to `/api`; Nginx forwards this prefix to the gateway
without stripping it and serves the frontend through its Nginx container.
The gateway routes requests to auth, catalog and order using Compose service
names on port 8000. `/api/auth/me` decodes the JWT in the gateway; the auth
service itself implements register/login. Gateway order creation derives
`user_id` from the token, and order reads check that user's ownership.

Order creation fetches each product and snapshots its name and integer price,
computes quantity times unit price, adds the order, flushes its ID, assigns items,
and commits. It then calls payment `/payments` synchronously. Payment creates
and commits a `created` payment, waits four seconds, commits `succeeded`, and
publishes an event to RabbitMQ followed by Kafka. The order consumer changes
the stored order to `paid`. The frontend polls order status every 1.5 seconds.

These steps span separate database and broker operations. There is no distributed
transaction or outbox, and a payment publication failure cannot atomically undo
the earlier commits. Preserve these boundaries unless a separately authorized
architecture task explicitly changes them.

# PostgreSQL / SQLAlchemy

- PostgreSQL 16 containers are separate for auth, catalog, order and payment.
  No direct cross-service foreign keys; `order_items.order_id` references the
  same service's `orders.id`. IDs are string UUIDs generated by models.
- Auth, catalog and order use synchronous SQLAlchemy engines with psycopg2 and
  independent `SessionLocal`. Request generators close sessions in `finally`.
  Auth disables autoflush; catalog/order use their configured defaults.
- Payment uses `create_async_engine` and asyncpg; `async_sessionmaker` disables
  autoflush and commit expiration. Its dependency yields inside an async context.
- Models declare their own `Base`. Application lifespan calls `create_all`
  (payment uses `run_sync` inside `engine.begin()`). No Alembic/migrations exist.
- `config.py` creates settings at import time. Most services require database
  or broker variables before imports. Importing/starting applications is not a
  service-free test; lifespan can create tables or connect to brokers.
- Money fields are integers; there is no documented currency/unit conversion
  contract. Preserve existing values and API representation.

# Kafka

Core Compose runs Apache Kafka 4.3.1 as one KRaft broker/controller, with
`kafka:29092` for the shared Docker network, host port 9092, controller port
9093, and single-replica offsets. Advertised host/bind address comes from core
env configuration. Analytics can share the Docker network or use a private
core-host endpoint, as described in README.

Payment `app/kafka.py` creates an `AIOKafkaProducer` and sends JSON-encoded bytes
using `send_and_wait` to `KAFKA_ANALYTIC_PAYMENT_TOPIC` (`payment-events`). It
does not set a record key or explicitly enable producer idempotence.
Analytics `app/consumer.py` starts `AIOKafkaConsumer` for `KAFKA_TOPIC`, inserts
each decoded record into MongoDB, and stops the consumer in `finally`. It does
not configure a consumer group or explicit offset commits. No application retry,
deduplication, dead-letter, or exactly-once mechanism is present.

The event builder `payment-service/app/events.py` produces:

| Field | Value |
| --- | --- |
| `event_id` | New string UUID |
| `created_at` | UTC ISO timestamp |
| `payment_id` | Payment UUID string |
| `order_id` | Order UUID string |
| `amount` | Integer payment amount |
| `status` | `succeeded` |

# RabbitMQ

RabbitMQ 3.13 management is in core Compose. Payment and order connect with
`aio_pika.connect_robust`. They declare `payment.events` using the library's
default exchange type (direct). Order declares `payment.results` and binds key
`payment.succeeded`. Names can be configured through their existing settings.

Payment sends `aio_pika.Message(json.dumps(event).encode())` without explicit
persistent delivery mode. Exchange/queue declarations do not request durability.
The order callback wraps decoding, order lookup and commit in `message.process()`;
normal exit acknowledges the message, and errors follow aio-pika's default
reject behavior. It uses the event's `order_id` and sets status `paid`.
There is no explicit prefetch, retry/DLQ, event-ID deduplication or outbox.
Do not describe this topology as guaranteeing exactly-once or durable delivery.

# Important Shared Components

There is no shared library. Similar settings, database dependencies, schemas
and declarative bases are owned by each service. Gateway `app/api_client.py`
centralizes its HTTP forwarding and upstream-error translation. Order
`app/api_clients/` owns its catalog/payment adapters. Payment's event builder
is the shared contract between its two publication paths; consumers use JSON
directly rather than importing that module across service boundaries.

Auth and gateway must use the same JWT secret and algorithm. Secrets remain in
ignored runtime configuration; only `infra/.env.core.example` and
`infra/.env.analytic.example` are versioned. Pydantic settings can also read
service-local `.env` files, so cloud checks must not inherit a production file.

# Testing Architecture

The tracked repository has no tests, pytest settings, backend lint/format/type
configuration, CI workflows, migration tests, testcontainers, or dedicated test
Compose topology. Do not invent a passing baseline. Frontend defines oxlint and
`tsc -b && vite build`; it uses the npm lockfile. Python dependency files are
partially pinned and do not have a lockfile. Install each backend separately
with Python 3.14 and its existing requirements; do not merge environment paths.

Source parsing and Compose `config --quiet` are safe supplemental checks, but
cannot detect runtime import failures or prove broker/database behavior. A
behavior change needs an isolated focused regression check; service startup
needs disposable PostgreSQL/RabbitMQ/Kafka/MongoDB as applicable. If cloud
Docker/services are unavailable, restrict task selection to changes that can be
adequately checked without them, or report no safe task. Never substitute a
production connection.

# Runtime / Docker Architecture

- `infra/docker-compose.core.yml`: Nginx, frontend, gateway, four transactional
  services, four PostgreSQL containers, RabbitMQ, Kafka.
- `infra/docker-compose.analytic.yml`: analytics and MongoDB. Both files use
  project name `orderflow` and can share its default network; start core first.
- Backend Dockerfiles use Python 3.14 slim and run `uvicorn app.main:app` on
  internal port 8000. Frontend builds using Node 22/npm ci and serves built
  assets using Nginx. Root Nginx exposes port 8080 by default.
- Gateway/auth/catalog/order/payment/frontend and databases use Docker-network
  connectivity; RabbitMQ 5672/15672, Kafka 9092, analytics 8005 and Nginx 8080
  are published by default. Bind/exposure settings matter in disposable clouds.
- Database and broker dependencies have health checks; application dependencies
  generally use `service_started`, which is not proof of application readiness.
- Named volumes preserve each PostgreSQL database, Kafka data, and MongoDB.
  README's ordinary `down` retains volumes. Do not run destructive volume cleanup
  against an existing environment.
- Analytics starts its Kafka consumer as a background task and cancels/awaits
  it on shutdown, then closes MongoDB. Payment and order manage broker clients
  in lifespan. Inspect current source when touching lifecycle code.

A cloud setup must be published and separately verified in Codex Cloud using
this repository and these commands. Repository docs do not themselves configure
a cloud environment, grant GitHub authentication, or create a schedule.
